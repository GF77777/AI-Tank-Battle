# 对战入口异步加载与推理轻量化计划

## Summary

修复点击“对战”和“排位”时主线程被模型初始化阻塞的问题，同时采用用户选择的两种方案：**标题界面后台预加载** + **点击时尚未就绪则显示加载页**，并为主程序使用轻量推理初始化。

静态调用链已明确：首次点击会同步导入 PyTorch、创建 DQN、读取模型，还会分配约 307MB 的训练回放数组；这些操作都发生在 Pygame 单线程事件循环内，因此窗口会短暂停止响应。模型文件本身只有 667,976 字节，磁盘读取不是主要疑点。

## Current State Analysis

- `main.py:25-51` 的事件分发、更新和渲染均在同一个主线程；任意同步耗时都会直接表现为界面卡顿。
- `game/core.py:369-384` 的 `_ensure_agent()` 在首次进入时同步执行：
  - `from ai.dqn import DQNAgent`，首次导入 PyTorch；
  - `DQNAgent(STATE_DIM, S.N_ACTIONS)`，构建网络、优化器和训练回放池；
  - `agent.load(path)`，反序列化并迁移模型参数。
- `game/core.py:386-403` 的 `_start_versus()` 与 `_start_pure()` 都先调用 `_ensure_agent()`，所以两个入口有相同的首次阻塞路径。`dqn_agent` 成功后会缓存，同一进程内后续进入和重开不应重复承担模型加载成本。
- `ai/dqn.py:27-36,62-76` 默认创建 `ReplayBuffer(100000,384)`。仅 `states/next_states` 两个 float32 数组就占 `2 × 100000 × 384 × 4 = 307,200,000` 字节，人类对战只做推理，并不需要这些训练数据。
- `ai/dqn.py:119-134` 的模型读取与权重迁移也是同步工作；但 `models/dqn_tank.pth` 仅约 668KB，相比 PyTorch 导入和大数组分配更不是首要来源。
- `game/level.py:100-133` 的地图仅是 17×17 字符网格转换；`game/avatars.py:17-44` 和 `game/sprites.py:618-626` 均有缓存，头像池也已在 `Game` 初始化时触及，属于次要因素。
- `game/playtest.py:38-40` 的开局只生成会话 ID，不在点击时写文件，不是本次卡顿主因。
- 现有 `start_notice` 在 `game/core.py:2620-2625` 固定显示模型缺失文案，没有加载中或加载失败状态，也没有任何异步加载机制。

## Proposed Changes

### 1. 先记录冷启动基线并保留同步路径证据

验证辅助操作，不修改生产逻辑：

- 用临时 `time.perf_counter()` 计时脚本分别记录首次 PyTorch/DQN 导入、`DQNAgent` 构造和 `agent.load()` 的耗时，以及默认回放池实际分配字节数。
- 同时记录模型已缓存后的再次进入，区分“首次模型初始化”与“每局地图重置”，避免把两类卡顿混为一谈。
- 临时脚本与输出放在系统临时目录，不改模型、存档或训练数据。

### 2. 主程序启动唯一的后台预加载

文件：`main.py`、`game/core.py`

- `main.py` 在创建 `Game` 后、进入事件循环前调用一次公开的 `start_agent_preload()`；不在 `Game.__init__` 自发启动线程。
- 因此训练、评估、RL `VersusEnv`、测试和 `play_ai.py` 的现有同步/注入式模型管理不受影响，也不会在 headless 环境意外读取模型或创建线程。
- `Game` 新增最小状态：
  - `_agent_queue`：worker 向主线程传递结果；
  - `_agent_thread`：保证只启动一个 daemon worker；
  - `_agent_status`：`idle/loading/ready/missing/failed`；
  - `_pending_ai_mode`：点击加载期间等待进入的 `pure/versus`，否则为 `None`。
- worker 内完成模型路径检查、PyTorch/env 导入、DQN 创建和模型读取；所有成功或异常结果只 `put()` 到队列一次。
- worker 不调用任何 Pygame 接口，也不直接修改 `dqn_agent`、状态机、提示页或其他 `Game` 字段，避免跨线程渲染和半初始化状态。

### 3. 主线程非阻塞接收结果并自动进入

文件：`game/core.py`

- 新增 `_poll_agent_preload()`，在 `Game.update()` 的非 `PLAYING` 提前返回之前执行 `get_nowait()`，任何情况下都不等待 worker。
- 成功时由主线程先安装 `_build_foe_state` 和 `_decode_vs_action`，再发布 `dqn_agent` 并标记 `ready`，保证 AI 决策看到完整初始化结果。
- 若存在 `_pending_ai_mode` 且仍处于标题状态，清除等待与加载提示，按原入口自动进入对应模式；没有其他等待时只缓存模型，不擅自开局。
- 缺失与损坏分别进入 `missing/failed`，有等待入口时显示相应提示，不会永久停留在加载页。
- `_ensure_agent()` 不再同步导入或读取模型：已就绪立即返回；未就绪时记录调用方是纯对战还是排位、显示加载页并按需启动预加载。模型已缓存后的重开沿用现有快速路径。

### 4. 人类对战跳过训练回放池分配

文件：`game/core.py`

- 仅后台为真人游戏创建推理 Agent 时使用现有参数 `DQNAgent(..., buffer_capacity=0)`，使 `states/next_states` 等回放数组为空，不再为主程序分配约 307MB 无用训练数据。
- 不修改 `ai/dqn.py` 的默认容量、网络结构、模型迁移、`act()` 或训练逻辑；`train.py` 仍使用自己的训练容量，`play_ai.py` 和 `evaluate.py` 也不在本次范围内调整。
- 模型权重、384 维状态、动作空间、AI 决策与奖励完全不变，仅省去人类对局用不到的回放存储。

### 5. 加载页、失败反馈与取消行为

文件：`game/core.py`

- 扩展现有 `start_notice` 渲染，不再固定使用 `versus_1/versus_2`，按提示类型映射双语文案：
  - `versus`：保留模型缺失提示；
  - `agent_loading`：显示“AI 模型加载中… / 完成后自动进入”；
  - `agent_failed`：显示模型加载失败及检查/重训提示。
- 加载页使用现有标题布局，不新增独立状态机或子进程；模型就绪后由轮询自动关闭并进入等待的模式。
- 加载中的 Enter 和鼠标点击不重复触发加载或开局；Esc 只取消本次 `_pending_ai_mode` 并关闭提示，后台加载继续完成并缓存。
- 取消后再次点击可直接使用已缓存模型；若仍在加载则重新挂接等待模式。离开标题等现有清理路径同步清除等待标记，避免以后意外自动开局。

### 6. 同步现有说明

文件：`docs/GDD.md`、`docs/UI设计规范.md`

- GDD 记录真人游戏后台预加载、零容量推理回放池、模型缓存及训练路径不变的约束。
- UI 规范补充加载中、缺失、失败提示及“Enter/点击不重复触发、Esc 取消进入但继续缓存”的交互。
- 仅更新现有文档版本与相关条目，不新增其他说明文件。

## Assumptions & Decisions

- 首要修复对象是每次进程首次加载 DQN 造成的主线程停顿；静态代码已证明该同步路径存在，具体耗时占比以基线计时为最终确认。
- 两种用户选择合并实施：正常停留标题时后台提前加载；用户抢先点击时仍能看到加载页并自动进入，而不是无反馈地卡住。
- 使用标准库 `threading` 与 `queue`，不新增依赖，不使用子进程，不让 worker 接触 Pygame。
- 不为加载页设置虚假进度条或计时动画；只表达真实状态，模型就绪后自动进入。
- 不修改地图、头像、精灵、音频、战斗数值、模型文件、训练参数、RL 384 维观测或奖励。

## Verification

1. 运行 `python -m compileall main.py game ai`，确认语法通过。
2. 用可控的临时阻塞 loader 验证：点击两个入口均立即返回，标题仍能 `update()/render()`；不会创建第二个 worker，加载完成后只自动进入一次。
3. 分别覆盖“预加载完成后点击”和“加载中点击”：纯对战与排位进入正确模式；重开、返回标题再进入均复用同一 Agent。
4. 加载中连续 Enter/点击不重复开局；Esc 取消后即使模型完成也停留标题，再次点击可正常进入；失败与缺失不会永久等待。
5. 用真实 `models/dqn_tank.pth` 完成后台加载，确认 `buffer.capacity == 0`、回放数组不占默认约 307MB，模型推理动作有效；对比基线记录点击阻塞与冷启动耗时。
6. 模拟模型缺失、损坏和 worker 异常，确认提示类型、队列接收和后续菜单操作正常，无未捕获线程异常导致的状态卡死。
7. 渲染加载中/缺失/失败页，检查双语文案与提示无重叠；窗口事件在后台加载期间持续处理。
8. 验证普通 `Game()`、`VersusEnv`、`train.py`/`evaluate.py` 的构造路径不会自发启动预加载；训练默认回放池、DQN 网络与加载逻辑不变。
9. 运行 RL `reset()/step()` 回归，确认状态仍为 384 维有限数值，奖励、随机序列和模型接口不受本次表现层加载优化影响。
